# python: mux helpers write_mux(any pattern), set_one_mux(k), mux_element_mask

- **Commit:** ebd298cc62a922d2b60f0659af902d02200a6733 (branch python-mux-helpers)
- **Date:** 2026-10-18
- **Files:** python/ultr4rick/device.py, python/ultr4rick/version.yaml
- **Versions:** firmware unchanged, python 0.1.10 -> 0.1.11

## Why
The maintainer asked for a way to write any pattern on the MAX14866 and a `set_one_mux(1..8)` that connects
element k to both TX and RX.

## What changed
- `write_mux(value)`: takes an int (any base) or a hex string, raises `ValueError` outside 0..0xFFFF, and always
  sends 4 hex digits (`write mux 0003`). Non-hex strings are no longer passed through verbatim.
- `mux_element_mask(k, tx=True, rx=True)` (static): RX bit `1 << 2(k-1)`, TX bit `1 << (2(k-1)+1)`.
- `set_one_mux(k)`: `write_mux(mux_element_mask(k))`, so element 1 -> 0x0003 ... element 8 -> 0xC000.
- Mapping from the U17 netlist (`hardware/MUX.kicad_sch`): NO(2k-2) and NO(2k-1) go to the element's U.FL
  (U18-U21, U26-U29); even COMs are on MUX_IN -> R77 -> ECHO_IN (RX), odd COMs on MUX_OUT -> R78 -> TX.

## Verification
Fake serial port: elements 1..8 send 0003, 000C, 0030, 00C0, 0300, 0C00, 3000, C000; `write_mux("ffff")` -> FFFF;
out-of-range values and k = 0, 9 raise. **Not verified on hardware**: the board was not enumerated on USB. The
bit n <-> SWn order (MSB first) is still to be confirmed on the board.
